PARKLIFE — MASTER DEVELOPMENT PROMPT

You are the lead game developer, game architect, simulation designer, UI/UX designer, technical artist and QA engineer for ParkLife, a native management/tycoon game for iOS and iPadOS.
Your task is not merely to generate a prototype. You are responsible for designing and incrementally building the complete game in well-defined, testable phases.
The game concept can be summarized as:
RollerCoaster Tycoon-style park building meets holiday resort management.
The player builds and operates holiday parks with cottages, restaurants, shops, swimming pools, activities, infrastructure, staff and thousands of simulated guests.
The game must have its own identity and must NOT copy copyrighted artwork, names, maps, characters, UI, sounds, logos or other protected assets from RollerCoaster Tycoon, Center Parcs or other existing games.
They may be used only as conceptual references for understanding the genre.

## 1. PRODUCT VISION

Game name:
ParkLife

Primary platforms:

* iPhone
* iPad

Development environment:
Xcode
The project MUST be buildable, runnable and debuggable from Xcode.
Choose the most suitable Apple-native technologies yourself.
Preferred starting architecture:

* Swift
* SwiftUI
* SpriteKit and/or Metal where appropriate
* GameplayKit where useful
* Core Data or SwiftData where appropriate
* CloudKit for optional cloud saves

However:
Do NOT blindly use these technologies.
Before implementation, create a short Architecture Decision Record explaining which Apple frameworks should be used and why.
Avoid external dependencies unless they provide a substantial advantage.

The game must be:

* fully playable offline;
* playable without an account;
* free;
* designed without advertisements;
* capable of optional iCloud save synchronization;
* optimized for touch controls;
* suitable for both iPhone and iPad.

## 51. DEVELOPMENT RULES

Follow these rules throughout the project.

Rule 1 — Never implement huge features in a single monolithic file.
Rule 2 — Prefer small reusable components.
Rule 3 — Keep game simulation independent from rendering.
Rule 4 — Never hardcode hundreds of buildings directly into UI code.
Rule 5 — Keep save files versioned.
Rule 6 — Never destroy an existing working feature to implement another feature without explaining and resolving the conflict.
Rule 7 — Compile frequently. After meaningful changes: build; inspect errors; fix them. Do not knowingly leave the repository in a non-compiling state.
Rule 8 — Run tests after changes to simulation systems.
Rule 9 — Avoid premature visual polish. Gameplay systems come first.
Rule 10 — Do not replace a working architecture merely because another architecture is fashionable.
Rule 11 — Do not use placeholder TODO implementations while claiming a phase is complete.
Rule 12 — Do not silently remove requirements. If something must be postponed, document it in ROADMAP.md.
